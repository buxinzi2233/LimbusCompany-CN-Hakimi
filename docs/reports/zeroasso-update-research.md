## 三、具体对照教训

### 1. 战斗条件：先写清所有者，再谈句式漂亮

定位：`Skills_Enemy-a1c10p1.json` → `id=9105902` → `level=1` → `coinlist[1].coindescs[1].desc`。

- 旧版：“若自身拥有[流血]，则对目标施加等同于**其强度一半**的[流血]层数……”
- 新版明确写成：“若自身带有[流血]，则对目标施加(**自身的[流血]强度/2**)层[流血]……”
- 韩文同一记录先指定 `자신에게`，再引用相应强度；当前采用新版，将所有者明确出来，并保留最多5层、每回合最多1次、向下取整。

下次校对逐项勾选：**触发时机 → 条件 → 数值所有者 → 受益/受害目标 → 强度/层数 → 上限 → 次数限制 → 取整规则**。不能把“其”当作足够精确的机制代词。

同组 `9105903` 的技能伤害、最终威力与不可摧毁硬币条件也各有对象；格式规范不等于机制已经正确。已有 `Passives.json` 中 `1041621` 的摘要仍比长说明多出受击增加震颤强度的描述，上游新版没有自动消除此矛盾，仍需后续按技能数据或实战确认，不能宣称本轮已解决。

### 2. 广播文风：区分可确认纠错与译法取舍

定位：`StoryData/S1000B.json`。

- `id=2`：旧版“导览地图由于尚未彻底织结完成”，零协会采用“1F的导览图尚未完善”。韩文确有 `매듭`（结）的用词，因此**不能把旧版的织结意象直接定性为凭空编造**；本轮是跟随上游的广播体处理。以后遇到此类世界观双关，应保留源词位置，再决定是否需要体现。
- `id=6`：旧版“为了各位顾客今天也能享受……希望大家全力以赴”，新版“请大家致力于为客人们提供有价值的购物体验”。新版更明确服务行为的主体；不要因为上一句在欢迎顾客，就把后一句的所有代词一律归给顾客。
- `id=0–6` 的 `teller/title/content` 一起查，分别区分“广播”“西西弗百货”和正文，不能只替正文留下旧场所名称。

结论：不要把“比旧版顺口”自动写成“原译事实错误”，也不要把文学性更强自动写成“更忠于原文”。

### 3. 探索文本：稳定键之外，还需要说话人与显示名称

定位：`RPGSystem/rpg-loc-dialogue-floor-1.json`，`D1092/texts.index=0` 与 `D1093/texts.index=1`。

本轮跟随上游将“迫切的顾客”对齐为“绝望的顾客”、“焦虑的顾客”对齐为“焦急的顾客”。这是同 `key + index` 的显示称呼更新，不是把人物合并成一个新角色。

下次必须同时对齐 `speaker`、对应 NPC 的 `displayName`、任务引用及正文；不以数组所在行号代替记录身份。`model`、`id`、`key`、`index` 等身份字段不得因中文称呼变化而被翻译或重排。

### 4. 格式层：上游原包与本项目发布资源不是同一个验收对象

- 上游原包普遍保留 `[ChargeRouge]`、`[Vulnerable]` 等词条 ID；项目规则要求机制引用中文化。工作区采用最新版同 ID 名称，但**原包保持原样**，不得先加工再声称“官方原版”。
- `[OnSucceedAttack]`、`[WhenUse]` 等触发标记不是普通状态名，保留原标记；不能以“含英文”直接删除引擎标记。
- `[BloodyMucus]` 的显示名本身含方括号，直接包裹会产生 `[洗礼[赤红]]`；工作区使用 `[洗礼（赤红）] `。旧章 `PhantomIncision` 同理采用“剑痕（残像）”，名称表与引用一起对齐。
- 原包的单省略号转为双省略号，关键词后补半角空格；这种本地格式适配不意味着上游所有相异格式都已被证明会在游戏中出错。
- `MainUIText-a1c10p1.json` 的 `9128_chapter_notice_popup_desc` 在韩文与上游中文中都存在交叉闭合标签；本轮采用新版用词，同时将六组结束标签改为 `</u></b></mark></color>`，不是照搬错误的闭合顺序。

## 六、下次汉化的最短工作清单

1. 固定官方发布标签、附件 SHA-256 与客户端版本；查[本地参考版本](../../references/README.md)，不要只看文件夹名。

4. 数组按 `id/key/level/index` 对齐；先报告重复身份，不能静默以最后一条覆盖前一条。

6. 翻译与格式适配分层；词条名中文化，触发标记保留，动态占位符一对一，标签严格 LIFO。
